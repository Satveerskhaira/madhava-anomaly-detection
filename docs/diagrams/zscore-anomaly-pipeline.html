Z-Score Anomaly Pipeline

A z-score check runs as a batch job on every 2-hour load in VPC 1, where BigQuery lives. It writes anomalies and the flagged transactions to their own tables. The web app in VPC 2 reads those tables over JDBC through Private Service Connect, and refreshes when each run finishes.

  • 10M claims a day
  • 12 batch runs a day
  • VPC 1 · EDP, BigQuery
  • VPC 2 · web app on GKE
  • Private Service Connect between them

How it fits together

VPC 1 · EDP

Batch job computes z-scores

Every 2 hours a BigQuery SQL job compares each client's new window with its 8-week baseline. Hits go to anomalies, and every claim behind them goes to anomaly_transactions.

VPC 2 · App

UI refreshes on run complete

The job publishes a run-complete message. The app pushes it to open browsers, which then fetch the new results. A 5-minute poll covers anyone who missed it.

Through PSC

JDBC reads the anomaly tables

The Spring Boot API uses the BigQuery JDBC driver. Each query is a BigQuery job over HTTPS to the PSC endpoint. Nothing holds a live connection open, and claims are not copied into VPC 2.

    The z-score, and which transactions get loaded

    z = (observed − mean) ÷ stddev · flag when |z| ≥ 3
    • Observed is a client's total in the new 2-hour window, for each metric: claim count, paid amount, reject rate.
    • Mean and stddev come from the same weekday and the same 2-hour slot over the last 8 weeks. Monday 08:00 is compared with past Mondays at 08:00, so normal daily and weekly swings don't flag.
    • Guards against noise. Skip a client with fewer than 4 weeks of history. Put a floor under stddev, for example 5% of the mean, so a very flat history doesn't turn a small change into a huge z. Set a minimum volume per window.
    • Per-client thresholds. 3 is the default. Clients can be tuned up or down in a small settings table the job reads.
    Which transactions are loaded

    For every flagged client window, the job loads all of that client's claims in the window into anomaly_transactions. When the flag is on reject rate, it loads the rejected claims only. Each claim also gets its own z-score, its paid amount per unit against that drug's normal, so reviewers can sort the most unusual claims to the top.

    How much data (example)

    If 20 client windows flag in a run and each holds about 2,000 claims, that is 40,000 rows per run, or roughly 500,000 a day. That's small for BigQuery. Partition by run date and expire partitions after the review period, for example 180 days.

    The batch job's SQL

    Three statements. The baseline is rebuilt once a day. The z-score and the transaction load run every 2 hours. Project, table and column names are placeholders.

    1. Daily: rebuild the baseline
    -- Mean and stddev per client, metric, weekday and 2-hour slot, last 8 weeks.
CREATE OR REPLACE TABLE edp_anomaly.baseline_stats CLUSTER BY client_id AS
WITH w AS (
  SELECT client_id,
         EXTRACT(DAYOFWEEK FROM received_ts)    AS dow,
         DIV(EXTRACT(HOUR FROM received_ts), 2) AS slot,
         DATE(received_ts)                      AS d,
         CAST(COUNT(*) AS FLOAT64)              AS claim_count,
         CAST(SUM(paid_amount) AS FLOAT64)      AS paid_amount,
         SAFE_DIVIDE(COUNTIF(claim_status = 'REJECTED'), COUNT(*)) AS reject_rate
  FROM edp.claims
  WHERE received_date BETWEEN DATE_SUB(CURRENT_DATE(), INTERVAL 56 DAY)
                          AND DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)
  GROUP BY client_id, dow, slot, d
)
SELECT client_id, dow, slot, metric,
       AVG(value) AS mean, STDDEV_SAMP(value) AS stddev, COUNT(*) AS n
FROM w UNPIVOT (value FOR metric IN (claim_count, paid_amount, reject_rate))
GROUP BY client_id, dow, slot, metric;
    2. Every 2 hours: score the new window
    -- @window_start is the slot start, @run_id comes from the batch job.
INSERT INTO edp_anomaly.anomalies
  (anomaly_id, run_id, client_id, window_start, metric, observed, mean, stddev, z, severity)
WITH cur AS (
  SELECT client_id,
         CAST(COUNT(*) AS FLOAT64)         AS claim_count,
         CAST(SUM(paid_amount) AS FLOAT64) AS paid_amount,
         SAFE_DIVIDE(COUNTIF(claim_status = 'REJECTED'), COUNT(*)) AS reject_rate
  FROM edp.claims
  WHERE received_date = DATE(@window_start)          -- one partition
    AND received_ts >= @window_start
    AND received_ts <  TIMESTAMP_ADD(@window_start, INTERVAL 2 HOUR)
  GROUP BY client_id
),
scored AS (
  SELECT o.client_id, o.metric, o.observed, b.mean, b.stddev,
         SAFE_DIVIDE(o.observed - b.mean, GREATEST(b.stddev, b.mean * 0.05)) AS z
  FROM cur UNPIVOT (observed FOR metric IN (claim_count, paid_amount, reject_rate)) o
  JOIN edp_anomaly.baseline_stats b
    ON b.client_id = o.client_id AND b.metric = o.metric
   AND b.dow  = EXTRACT(DAYOFWEEK FROM @window_start)
   AND b.slot = DIV(EXTRACT(HOUR FROM @window_start), 2)
  WHERE b.n >= 4                                      -- at least 4 weeks of history
)
SELECT TO_HEX(MD5(CONCAT(client_id, '|', CAST(@window_start AS STRING), '|', metric))),
       @run_id, client_id, @window_start, metric, observed, mean, stddev, z,
       IF(ABS(z) >= 5, 'HIGH', 'MEDIUM')
FROM scored
WHERE ABS(z) >= 3;
-- A rerun of the same window deletes its rows first, or use MERGE on anomaly_id.
    3. Every 2 hours: load the flagged transactions
    INSERT INTO edp_anomaly.anomaly_transactions
  (run_date, run_id, client_id, window_start, metrics, max_z,
   claim_id, received_ts, pharmacy_id, prescriber_id, member_id, drug_ndc,
   quantity, days_supply, paid_amount, claim_status, claim_z)
WITH flagged AS (                                       -- one row per client window
  SELECT client_id, window_start,
         ARRAY_AGG(metric) AS metrics, MAX(ABS(z)) AS max_z,
         LOGICAL_AND(metric = 'reject_rate') AS rejects_only
  FROM edp_anomaly.anomalies
  WHERE run_id = @run_id
  GROUP BY client_id, window_start
)
SELECT DATE(@window_start), @run_id, f.client_id, f.window_start, f.metrics, f.max_z,
       c.claim_id, c.received_ts, c.pharmacy_id, c.prescriber_id, c.member_id, c.drug_ndc,
       c.quantity, c.days_supply, c.paid_amount, c.claim_status,
       SAFE_DIVIDE(SAFE_DIVIDE(c.paid_amount, c.quantity) - n.mean_ppu, n.stddev_ppu) AS claim_z
FROM flagged f
JOIN edp.claims c
  ON c.client_id = f.client_id
 AND c.received_date = DATE(@window_start)
 AND c.received_ts >= f.window_start
 AND c.received_ts <  TIMESTAMP_ADD(f.window_start, INTERVAL 2 HOUR)
LEFT JOIN edp_anomaly.ndc_baseline n ON n.drug_ndc = c.drug_ndc   -- daily, like baseline_stats
WHERE NOT f.rejects_only OR c.claim_status = 'REJECTED';

    JDBC from the web app

    • There is no live connection to BigQuery. A JDBC connection to BigQuery is a client object. Each query runs as a BigQuery job over HTTPS, typically 1 to 3 seconds. Keep the pool small and cache results per run.
    • The route is Private Service Connect. The driver calls bigquery.googleapis.com. A private DNS zone in VPC 2 resolves it to the PSC endpoint. Add bigquerystorage.googleapis.com too, because the driver can use the Storage Read API for larger results.
    • Jobs run and bill in the app project. ProjectId in the URL is where queries run. Use fully qualified table names to read from the EDP project.
    • Always use parameters and partition filters. Every UI query names a run date or window, so it reads a few MB, not the table.
    • Read-only. The API only selects from BigQuery. Review decisions go to Cloud SQL.
    application.yml
    # Google's BigQuery JDBC driver. Check the driver class and property
# names against the driver version you install.
spring:
  datasource:
    driver-class-name: com.simba.googlebigquery.jdbc.Driver
    url: >-
      jdbc:bigquery://https://www.googleapis.com/bigquery/v2:443;
      ProjectId=app-project;OAuthType=3;Timeout=60;
      EnableHighThroughputAPI=1
    hikari:
      maximum-pool-size: 10
      connection-timeout: 30000
# OAuthType=3 uses Application Default Credentials, which
# GKE Workload Identity provides. No key files.

    How the web UI refreshes

    • The push comes from the run, not from BigQuery. When the batch job finishes, it publishes run-complete to Pub/Sub. The refresh notifier in VPC 2 pulls it through PSC and sends a server-sent event to each open browser.
    • The browser then fetches. It shows "New results" with the run time and reloads the feed from the API. The API queries BigQuery once per run and filter, then serves from Redis.
    • Polling covers gaps. Browsers also call /api/runs/latest every 5 minutes. That call reads one cached value, so it costs nothing.
    • Set the load balancer for long-lived requests. Server-sent events need the backend service timeout raised, for example to an hour, and a heartbeat from the server every 30 seconds. With the default timeout the stream drops after 30 seconds.
    • Always show "data as of". Taken from run_log, so a reviewer can see a late run.

    Recommendation

    Start with a BigQuery scheduled query in VPC 1. The z-score is plain SQL, so nothing else needs to run there. Move to Cloud Workflows or Dataform when you need a load-complete trigger, automatic retries or multi-step dependencies. Use the Spring Batch CronJob only if the app team can't deploy into the EDP project. The SQL is the same in all three, so you can switch later. The web app stays read-only toward BigQuery: JDBC reads plus one Pub/Sub subscription.
