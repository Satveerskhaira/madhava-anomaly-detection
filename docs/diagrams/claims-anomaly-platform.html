Claims Anomaly Platform

End-to-end design for finding claim anomalies in BigQuery and serving them to a React app in a separate VPC through Private Service Connect. It includes client-specific rules, suppressions and saved filters. Pick a flow to watch it move through the system.

  • 10M claims a day
  • 12 detection runs a day
  • Private Service Connect to Google APIs
  • Spring Boot on GKE
  • React UI

Step 1 of 1App VPC

    How a model trained on history flags new claims

    The model learns what normal looks like from months of past claims. Every 2 hours it scores the new claims against that learned normal. The one rule that matters: training and scoring use exactly the same feature code.

    Learn

    Weekly or monthly, on history
    1. Claims history12 months, all clients. Known outages and confirmed incidents removed or labeled.
    2. Build featuresThe same Dataform code that runs every 2 hours.
    3. Fit the modelIt learns normal patterns per client, drug class and pharmacy.
    4. Set thresholdsScore the history and pick a cut-off per segment, for example the top 0.5%.
    5. Save a versionModel, thresholds and feature list saved together.

    Score

    Every 2 hours, on new claims
    1. New windowAbout 830k claims.
    2. Build featuresSame code, so the model sees what it was trained on.
    3. ScoreEach claim and each client window gets a score against the learned normal.
    4. ExplainTop reasons per flag, such as quantity far above this drug's norm.
    5. CombineWith baselines and client rules into one severity.
    Claim level (example)

    A claim for 240 tablets of a drug that, for this client, is filled at 30 to 90 tablets in 98% of history, at a pharmacy that has never filled it for them. The claim scores 0.97. Reasons: quantity against this drug's norm, new pharmacy and drug pair.

    Rolled up to the client (example)

    In the 10:00 to 12:00 window, 3.2% of client C-4411's claims scored above threshold against a usual 0.4%. That raises a client-level anomaly. Drill-down lists the high-scoring claims, ranked by score.

    • Two levels of model. Claim-level models score every new claim and are trained on a sample, for example tens of millions of claims spread across clients and drug classes. Window-level models score each client's 2-hour totals and train on every past window.
    • Only scores are stored. Claim scores keep the claim id, score and reasons, never claim contents, so there is still one copy of the claims.
    • New clients. Until a client has about 8 weeks of history, score them with a model trained on similar clients.
    • Keeping it honest. Watch feature drift each run and retrain on a schedule. A new version runs in shadow, scored but not shown, until it beats the live one on analyst-confirmed cases.

          Run the pipeline in EDP or in the app project?

          Run in the EDP project

          Good

          • Claims and history never leave EDP, so one governance boundary.
          • Compute sits next to 12 months of data. Features, training and reruns are just queries.
          • The app only reads results, so VPC-SC needs a read rule and nothing else.
          • Late data and backfills are cheap to rerun.

          Watch out

          • The app team may not have deploy rights in EDP, so models ship through the data team's process.
          • Shares BigQuery capacity with other EDP workloads.
          • Your library must be packaged as a container or exported to ONNX.
          Run in the app project

          Good

          • The app team owns the model end to end on GKE and Spring Boot it already runs.
          • Your library runs as it is, with your own release cadence.
          • Scoring can be very fast once features arrive.

          Watch out

          • Features still have to be built in BigQuery, so the pipeline spans both projects anyway.
          • Every run reads and writes across PSC, and needs VPC-SC rules for both directions.
          • Pulling raw claims puts PHI in the app cluster and makes training pull billions of rows.
          • Two places to monitor when a run is late.

          Recommendation

          Run the pipeline in EDP with pluggable detectors, the recommended mix above. Start with BigQuery ML for seasonal and volume baselines. Bring your custom library in through option B when its models export to ONNX, and option C when they don't. Keep the app a reader of results.

          If the app team can't deploy into EDP or hand models over, use option D, which moves features and not claims. Avoid option E unless a model truly needs raw claims.

          1. Phase 1. BigQuery ML forecast plus client rules go live. The detector registry and the shared scores table are in place from day one.
          2. Phase 2. Your library trains on Vertex AI and scores through B or C in shadow mode, compared against analyst decisions.
          3. Phase 3. With a few months of analyst labels, add claim-level scoring and a supervised model that re-ranks alerts. Promote whichever detectors win in shadow.

          How to pick quickly

          • Does your library export to ONNX? Yes, use B. No, use C.
          • Can models be deployed into EDP, by you or the data team? No, use D.
          • Does any model need raw claims that can't be built as BigQuery features? Only then consider E.

          The contract every detector meets

          This is what lets BigQuery ML and your library run side by side. Each detector is a row in a registry, and every engine writes the same scores table.

          What your library implements
          # Same four calls whatever the engine. Pseudo-interface.
fit(features_table, train_window, config)
    -> model_version, thresholds, feature_list

score(features_table, model_version)
    -> rows in edp_anomaly.model_scores

explain(features_table, model_version)
    -> top reasons for each flagged row

export_onnx(model_version)          # optional
    -> gs://.../model.onnx           # enables option B
          Registry and shared scores table
          CREATE TABLE edp_anomaly.detectors (
  detector_id   STRING,
  engine        STRING,  -- BQML | ONNX_IN_BQ | VERTEX_BATCH | GKE
  granularity   STRING,  -- CLAIM | CLIENT_WINDOW | CLIENT_PHARMACY
  model_version STRING,
  feature_set   STRING,  -- version of the feature code
  scope_clients ARRAY<STRING>,  -- empty means all clients
  mode          STRING,  -- LIVE | SHADOW | OFF
  weight        FLOAT64,
  owner         STRING
);

CREATE TABLE edp_anomaly.model_scores (
  run_id STRING, window_start TIMESTAMP,
  detector_id STRING, model_version STRING,
  granularity STRING, client_id STRING,
  entity_id STRING,      -- claim_id for CLAIM rows
  score FLOAT64, threshold FLOAT64, flagged BOOL,
  reasons ARRAY<STRUCT<feature STRING, contribution FLOAT64>>,
  shadow BOOL
)
PARTITION BY DATE(window_start)
CLUSTER BY client_id, detector_id;

          Client rules and filters

          Clients get four kinds of configuration. Three change what detection produces, so they are copied to BigQuery for the run to read. The fourth only changes what someone sees in the app.

          Changes detection

          Threshold override

          Changes how sensitive the baseline is for one client and metric.

          Example: client C-4411, alert on claim count only when the score is 5 or more and the window has at least 500 claims.

          Stored in Cloud SQL, published to edp_rules.client_rules, used when scoring.

          Changes detection

          Custom rule

          A client-specific condition that creates its own anomaly, on a window total or on individual claims.

          Example: days supply over 30 on opioid agonists, 5 or more claims in one window, severity high, alert pharmacy ops.

          Stored in Cloud SQL, published to edp_rules.client_rules, evaluated each run.

          Changes detection

          Suppression

          Keeps known patterns from alerting. The hit is still recorded and marked suppressed, so nothing is lost.

          Example: ignore claim-count spikes on days 1 to 3 of each month for client C-4411, until 31 Jan 2027.

          Needs a reason and an end date. Published to edp_rules.suppressions.

          App only

          View filter

          Narrows the feed for one person or team. Detection and alerts are unchanged.

          Example: high severity, specialty drugs, my clients only.

          Saved views in Cloud SQL. The API applies them when it reads the feed.

          Rule lifecycle

          1. Draft
          2. Backtested
          3. Pending approval
          4. Active
          5. Retired
          • Backtested. Runs against the last 28 days before anyone can approve it.
          • Pending approval. A second person approves. Authors cannot approve their own rules.
          • Active. Takes effect at the next run. Each run reads a snapshot of the rules, so a mid-run edit changes nothing.
          • Retired. Kept for audit. Rolling back means reactivating an earlier version.

          Each run applies them in this order

          1. Roll up the new window per client and metric.
          2. Score against the baseline, using the client's threshold overrides where they exist.
          3. Evaluate custom rules for that client.
          4. Mark hits that match an active suppression.
          5. Merge duplicates, set severity, and record the rule id and version on every rule hit.
          What the rule builder sends (example)
          {
  "client_id": "C-4411",
  "name": "Long days supply on opioid agonists",
  "kind": "CLAIM",
  "scope": { "drug_class": "OPIOID_AGONIST" },
  "condition": { "field": "days_supply", "operator": "GT", "value": 30 },
  "fire_when": { "min_hits_per_window": 5 },
  "severity": "HIGH",
  "notify": ["teams:pharmacy-ops"]
}
          How the run evaluates every claim rule
          -- One fixed query for all clients. Rules are rows, never SQL text,
-- so a rule cannot change the query. Names are placeholders.
WITH hits AS (
  SELECT r.rule_id, r.rule_version, r.min_hits, c.client_id,
         r.operator, r.value,
         CASE r.field                      -- allow-listed fields only
           WHEN 'days_supply' THEN CAST(c.days_supply AS NUMERIC)
           WHEN 'quantity'    THEN CAST(c.quantity    AS NUMERIC)
           WHEN 'paid_amount' THEN c.paid_amount
         END AS v
  FROM edp.claims c
  JOIN edp_rules.run_snapshot r            -- rules pinned for this run
    ON r.client_id = c.client_id AND r.kind = 'CLAIM'
  WHERE c.received_date = DATE(@window_start)
    AND c.received_ts >= @window_start
    AND c.received_ts <  TIMESTAMP_ADD(@window_start, INTERVAL 2 HOUR)
    AND (r.scope_drug_class IS NULL OR c.drug_class  = r.scope_drug_class)
    AND (r.scope_pharmacy   IS NULL OR c.pharmacy_id = r.scope_pharmacy)
)
SELECT rule_id, rule_version, client_id, COUNT(*) AS hit_count
FROM hits
WHERE CASE operator
        WHEN 'GT'  THEN v >  value  WHEN 'GTE' THEN v >= value
        WHEN 'LT'  THEN v <  value  WHEN 'LTE' THEN v <= value
      END
GROUP BY rule_id, rule_version, client_id, min_hits
HAVING COUNT(*) >= min_hits;
-- Only the count is stored. Drill-down re-applies the same rule
-- version to list the claims, so claims are never copied.

          Guardrails

          • No SQL from users. Fields, operators and scope dimensions come from an allow-list the platform team owns. Window rules work the same way on the rollup metrics.
          • Access follows clients. People can create rules only for clients they are entitled to see, checked in the Rules service.
          • Backtest cost is capped. Preview runs a dry run first and sets a maximum bytes billed on the real query.
          • Limits keep runs predictable. For example, at most 50 active rules per client, and suppressions no longer than 90 days.
          • Everything is versioned and audited. Who changed what, who approved it, and which version produced each anomaly.

          • DNS does the routing. A private Cloud DNS zone points googleapis.com at the PSC endpoint, so the standard Java BigQuery and Pub/Sub clients work unchanged.
          • Everything in the app uses the VPC. GKE nodes are in the VPC already. Set the Cloud Run job to Direct VPC egress for all traffic so it also goes through PSC.
