Claims Anomaly Architecture

What runs in the EDP VPC, what runs in the application VPC, and which connections need to be live.

  • 10M claims a day
  • 12 loads a day, about 830k claims each
  • BigQuery data in the EDP VPC
  • UI and API in the application VPC

Do the VPCs need a live connection to BigQuery?

No standing connection is needed. The app sends BigQuery a request when it needs an answer, and BigQuery replies over its API.

Runs in EDP

Detection

Runs entirely inside BigQuery after each 2-hour load. The application VPC is not involved.

Runs in app, reads EDP

Dashboard

Reads a small anomalies table. It changes 12 times a day, so the app caches it per run and most page loads never reach BigQuery.

Runs in app, reads EDP

Drill-down

A live query when the analyst clicks, limited to one client, one window and one driver. Claims are shown on screen and never stored in the app.

The only traffic between the VPCs that nobody asks for is a run-complete message of about 1 KB, 12 times a day.

What happens, and where

Pick a flow. The numbers on the boxes match the steps underneath.

Claims table

Dataform workflow

Serving views

Authorized views with client filters and PHI masking. The only objects the app can read.

One run_log row and one Pub/Sub message per finished run.

React UI

API service

Cloud Run or GKE. Runs parameterized BigQuery queries and enforces which clients each person can see.

Case database

Postgres or Firestore. Status, assignee, notes and analyst labels.

  1. EDP VPC

    The 2-hour load lands in claims. About 830k claims per load go into the day partition.

  2. EDP VPC

    A completion event starts the Dataform workflow. It checks the row count against expected volume first and waits if the load looks partial.

  3. EDP VPC

    The workflow rolls up only the new window, per client, into client_window_metrics.

  4. EDP VPC

    Scoring compares each client's window with the same weekday and hour over the past 8 weeks. The change is attributed to drug, pharmacy, prescriber and plan, and results go to anomalies and anomaly_drivers.

  5. Crosses the boundary

    The workflow writes a run_log row and publishes a run-complete message to Pub/Sub. The app's API subscribes to it.

  6. App VPC

    The API drops the cached feed from the previous run and can pre-load the new one.

  1. App VPC

    An analyst opens the dashboard. The browser calls the API over HTTPS, and the API works out which clients that person may see.

  2. App VPC

    The API looks in its cache for the current run id. A hit returns immediately with no call to BigQuery.

  3. Crosses the boundary

    On a miss, the API sends one parameterized query for those clients to the anomalies serving view, over the BigQuery API.

  4. App VPC

    The result is cached until the next run. The API adds case status (open, confirmed, dismissed) from the case database.

  5. App VPC

    The UI shows the client-level feed sorted by severity, with a "data as of" time taken from the run.

  1. App VPC

    The analyst opens an anomaly. The API returns the driver breakdown from the cached run result, or reads anomaly_drivers if the cache is empty.

  2. App VPC

    The analyst picks a driver, such as one drug. The API fills a fixed query template. The driver column comes from an allow-list and every value is a query parameter.

  3. Crosses the boundary

    The query goes to the claims serving view. BigQuery reads one client's slice of the day partition, masks PHI columns and stops at the byte cap.

  4. App VPC

    Up to 200 claim rows go to the browser. The app shows them and does not store them.

  5. App VPC

    Confirm, dismiss or a note is saved in the case database with the anomaly id and the ids of the claims the analyst flagged.

Every connection and whether it is live

BigQuery has no connection to hold open. Each call is its own HTTPS request. A truly live dashboard would mean repeating queries, so the app caches per run instead.

Network and access

  • BigQuery is an API, not a server inside a VPC. The app calls bigquery.googleapis.com. The EDP VPC and the application VPC do not need peering for this design.
  • Private path. Turn on Private Google Access on the app subnets, or create a Private Service Connect endpoint for Google APIs. Traffic stays on Google's network and needs no public IP.
  • VPC Service Controls. If the EDP project sits inside a perimeter, add an ingress rule for the app's service account and use the restricted Google APIs address on the private path.
  • Identity and roles. One service account for the API. Give it BigQuery Data Viewer on the serving dataset only, and BigQuery Job User on the project that runs the jobs. Authorized views read claims on its behalf, so the app has no access to the claims table itself.
  • PHI. Policy tags mask member and prescriber identifiers by default, and clear values go only to roles that need them. Turn on data access audit logs and label each job with a hashed user id so a claim-level read can be traced to a person.
  • When peering would be needed. Only if the app must call something other than BigQuery inside the EDP VPC, such as a service on GKE.

The detection SQL

Shown for claim count. The real job repeats the scoring for paid amount, reject rate and days supply. Table and column names are placeholders. Windows are by arrival time, so a late claim lands in the window it arrives in.

1. Roll up the new window
-- Reads only the new rows in today's partition.
INSERT INTO edp_anomaly.client_window_metrics
  (client_id, window_start, claim_count, paid_amount, reject_count)
SELECT client_id, @window_start, COUNT(*), SUM(paid_amount),
       COUNTIF(claim_status = 'REJECTED')
FROM edp.claims
WHERE received_date = DATE(@window_start)
  AND received_ts >= @window_start
  AND received_ts <  TIMESTAMP_ADD(@window_start, INTERVAL 2 HOUR)
GROUP BY client_id;
-- A rerun deletes the window first so it is never counted twice.
2. Score against the same weekday and hour
-- Same weekday and hour over the past 8 weeks, from the small rollup.
WITH history AS (
  SELECT n.client_id, n.window_start, n.claim_count AS observed, h.claim_count AS past
  FROM edp_anomaly.client_window_metrics n
  JOIN edp_anomaly.client_window_metrics h
    ON h.client_id = n.client_id
   AND h.window_start <  n.window_start
   AND h.window_start >= TIMESTAMP_SUB(n.window_start, INTERVAL 56 DAY)
   AND EXTRACT(DAYOFWEEK FROM h.window_start) = EXTRACT(DAYOFWEEK FROM n.window_start)
   AND EXTRACT(HOUR FROM h.window_start)      = EXTRACT(HOUR FROM n.window_start)
  WHERE n.window_start = @window_start
),
stats AS (
  SELECT client_id, window_start, ANY_VALUE(observed) AS observed,
         APPROX_QUANTILES(past, 100)[OFFSET(50)] AS median,
         COUNT(*) AS weeks_of_history
  FROM history
  GROUP BY client_id, window_start
),
mad AS (
  SELECT s.client_id, s.window_start,
         APPROX_QUANTILES(ABS(h.past - s.median), 100)[OFFSET(50)] AS mad
  FROM stats s
  JOIN history h ON h.client_id = s.client_id AND h.window_start = s.window_start
  GROUP BY s.client_id, s.window_start
)
SELECT s.client_id, s.window_start, 'claim_count' AS metric,
       s.observed, s.median AS expected,
       SAFE_DIVIDE(0.6745 * (s.observed - s.median), m.mad) AS robust_z
FROM stats s
JOIN mad m ON m.client_id = s.client_id AND m.window_start = s.window_start
WHERE s.weeks_of_history >= 4;
-- Flag when ABS(robust_z) >= 3.5, then MERGE into anomalies on anomaly_id.
-- When mad is 0 (flat history), robust_z is NULL. Fall back to a percent-change rule.
3. Drill-down on the analyst's click
-- One of four fixed templates. The driver column (drug_ndc here) comes from an
-- allow-list in the API. Values are always query parameters.
SELECT claim_id, received_ts, pharmacy_id, drug_ndc, quantity, days_supply,
       paid_amount, claim_status,
       member_id                                  -- masked by a policy tag
FROM edp_serving.v_claims_drilldown
WHERE received_date = @window_date                -- partition filter, required by the table
  AND received_ts >= @window_start
  AND received_ts <  @window_end
  AND client_id   = @client_id                    -- clustering column
  AND drug_ndc    = @driver_value
ORDER BY paid_amount DESC                         -- order depends on the metric that fired
LIMIT 200;
-- Job settings: maximum_bytes_billed cap, labels {app: anomaly-ui, user: hashed id}.
-- Table option: require_partition_filter = true, so a query without a date filter fails.

When something goes wrong

If this happensThe system does this
The 2-hour load is late or partialThe workflow compares the row count with expected volume before scoring and waits. The UI shows the last run time and the next expected run.
BigQuery is slow or unreachableThe feed comes from cache with a "data as of" time. Drill-down shows a retry message. Case work continues because it lives in the app database.
The run-complete message is missedThe cache expires after 2 hours 15 minutes anyway, and the API checks run_log every few minutes.
A late claim changes a past windowThe next run rescores it and updates the same anomaly row. Open cases keep their notes.
A query scans too muchThe claims table requires a partition filter and every job has a maximum bytes billed cap, so the query fails instead of running up cost.

Build order

  1. Detection in EDP. Rollup, scoring, anomalies, drivers and run log. Backtest on 8 weeks of history before anyone sees an alert.

  2. Access path. Service account, serving views, masking and the perimeter rule. Run one test query from the app subnet.

  3. The app. API, anomaly feed, driver breakdown, claim list and case database.

  4. Events and feedback. Run-complete message and cache, alerts for high severity, and analyst labels kept for tuning.

Decisions to confirm

  • Which project runs the query jobs? Scans are billed to it. The app project keeps cost with the app team. The EDP project keeps it with the data owner.
  • Whose identity queries BigQuery? Suggested default is one service account, with the API enforcing client access and every job labeled with the user. Use each analyst's own credentials only if compliance wants BigQuery itself to enforce access per person.
  • Is the EDP project inside a VPC Service Controls perimeter? That decides the ingress rule.
  • Are member and prescriber identifiers shown clear or masked by default in the drill-down?

Perimeter rules, roles and network endpoints depend on how your organization sets up Google Cloud. Confirm them with cloud security before building the access path.
